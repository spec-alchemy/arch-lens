## 目标与判断标准

Arch Lens 的目标不是收集架构图，而是降低人理解现状、比较方案和做出决定的成本。好模型应满足：

- **有问题**：读者知道这张图在回答什么。
- **有边界**：能看出范围内外、职责归属和不讨论的内容。
- **有语义**：名称采用领域语言，关系说明原因而非只表示“有关”。
- **有证据**：现状图可追溯到需求、代码、测试、数据或访谈事实；设计图明确标为候选。
- **可扫描**：无需打开属性面板或阅读源码就能理解主干。
- **可决策**：图中信息足以暴露遗漏、冲突、耦合、无主职责或错误假设。

把 UML 当作一组互补视角，而不是一张包罗万象的总图。模型是对现实世界实体、行为和规则的刻意抽象；只保留对当前问题有解释力的信息。

## 从问题选择视图

| 要回答的问题 | 首选视图 | 常见补充 |
| --- | --- | --- |
| 谁希望系统达成什么目标？范围在哪里？ | 用例图 | 活动图、用例说明 |
| 业务中有哪些核心概念、规则和关系？ | 领域类图 | 状态图 |
| 一个业务目标怎样流转？谁负责每一步？ | 活动图 | 领域类图、状态图 |
| 一个具体场景中各职责如何协作？ | 时序图 | 组件图 |
| 能力由哪些稳定职责承担？通过什么接口协作？ | 组件图 | 时序图 |
| 一个重要实体如何跨阶段变化？ | 状态图 | 活动图、领域类图 |

选择规则：

1. 先写一句问题，再选图。
2. 先选一张能直接回答问题的图。
3. 只有存在另一种独立判断需求时才增加第二张图。
4. 不默认创建技术分层图、前后端图、微服务图或部署图。

## 视图预算与复用

预算针对准备持久进入 Change Pack 和批准图集的 `.puml`，不限制临时推理、IDE 预览或可再生成 SVG。

1. 默认一张主视图，通常最多三张。主视图应直接回答本次最重要的决策问题。
2. 生成前先列出拟修改或新增的视图，并为每张写明问题、独立决策价值、已有图复用判断和不可由简单文字替代的理由。
3. 第二、第三张只用于结构与行为等真正互补的判断；不能因为指南列出了六种图就各画一张。
4. 第四张及以后属于超额视图。逐张说明为什么不能合并，并在创建文件前获得当前会话中的人类明确同意。
5. 先更新已有业务模型，再考虑新增文件。不要按 Change Pack、AC、接口或测试案例建立平行图集。

合并与拆分按决策问题判断：

- 参与者、责任边界和生命周期相同的正常、失败、取消、超时和重试，优先放入同一时序图的 `alt/opt`、同一活动图的 guard 分支或同一状态图的转换。
- 结构和行为需要分别决策时，可以使用一张领域或组件图加一张活动、时序或状态图。
- 只有 Actor、业务边界、规则所有者、生命周期或人类需要作出的决定不同，才新增独立图。
- 图过密时先删除无关信息、换用更合适的图种或缩小问题；拆图不是默认的第一反应。

## 所有图的共同规则

### 命名

- 使用业务人员和产品人员能识别的统一语言。
- Actor 用角色名，如“值班护士”，不用具体姓名。
- 用例和活动用动宾短语，如“确认手术排程”。
- 实体、值对象、组件和状态用名词或名词短语。
- 消息用表达业务意图的动词，如“预留手术间”，不用 `POST /api/...` 或 `save()`。

### 范围和密度

- 一图一问；标题描述主题，`arch-lens: question` 写明审查问题。
- 主阅读路径尽量控制在一屏。节点超过约 20 个或交叉线明显增加时，优先按用例、能力或生命周期拆分。
- 使用 `package`、`rectangle`、swimlane 等表达真实边界，不用它们做纯装饰。
- 省略框架、日志、序列化、getter/setter 等不影响当前判断的信息。

### 事实、候选和未知

- 现状图只画有证据的事实。
- 候选设计在标题或 note 中写明 `Candidate`，并列出关键假设。
- 用 note 标记少量高价值约束；大量说明应回到需求或代码文档，不要塞满图面。
- 不确定关系不要画成确定关系；把它列为未决问题。

### 关系

- 每条非显然关系都应有方向、名称、角色、多重性、guard 或消息中的至少一种语义。
- 不用同一种箭头混合表达数据流、调用、依赖、所有权和继承。
- UML 关系应按其原义使用；拿不准时选择普通有向关系并写清标签，避免伪精确。

## 用例图

**回答**：哪些外部角色为了什么目标与系统交互，系统责任边界在哪里？

规则：

- Actor 是系统外部角色或外部系统，不是内部模块、数据库或类。
- 用例表达 Actor 可观察的目标结果，不是页面、按钮、CRUD 操作或内部函数。
- 使用一个明确的系统边界。边界外不画系统内部结构。
- Actor 与用例的关联表示参与，不等同于调用方向。
- `include` 仅表达必然复用的子目标；`extend` 仅表达在明确条件下插入的可选行为。
- 若 `include/extend` 只是为了少画几个椭圆或复用文案，删掉它。
- 对关键用例补充主成功场景、替代路径、前置条件和结果；通常用活动图或时序图承载，不把步骤塞入用例图。

审查问题：是否遗漏了受结果影响的角色？用例是用户目标还是界面功能？系统边界是否把外部职责错误吸收进来？

## 领域类图

**回答**：业务世界由哪些核心概念构成，它们有哪些稳定规则和关系？

规则：

- 从领域概念建模，不从表结构或 ORM 类反推命名。
- 区分实体和值对象：实体由身份和生命周期区分；值对象由值定义，通常不可变。
- 明确关键属性、业务标识和约束；省略审计列、框架注解和无关技术字段。
- 为关系标注角色名和多重性；无法确定多重性说明领域规则尚未厘清。
- 组合只用于“部分不能脱离整体独立存在且生命周期由整体控制”；聚合语义常含混，优先使用普通关联并写角色。
- 泛化只用于真实的可替换分类，不用于代码复用。
- 只在操作有助于判断实体职责或不变量时显示操作；不要罗列所有方法。
- 枚举只表达稳定封闭集合；频繁配置变化的字典不要伪装成枚举。

审查问题：哪些对象拥有规则？是否出现贫血实体和万能 Service？多重性与生命周期是否一致？同一概念是否被不同名称重复表达？

## 活动图

**回答**：一个业务目标如何从触发流转到结果，决策、并行、责任和业务数据在哪里？

规则：

- 一张图只描述一个业务目标或一个清晰子流程。
- 使用 swimlane/partition 表达参与角色或职责，不按 Controller/Service/Repository 分栏。
- 每个 decision 的分支写 guard，例如 `[库存充足]`；不要使用含糊的“是/否”而隐藏条件。
- 区分并行 fork/join 与互斥 decision/merge。
- 标出关键业务对象的产生、变更或交接；不展示每个函数调用。
- 对异常、取消、超时和补偿路径做有选择的展示，尤其当它们影响业务承诺时。
- 终点应表达业务结果，而不仅是“结束”。

审查问题：每一步由谁负责？分支条件是否完备且互斥？失败后系统和业务对象处于什么状态？是否存在无人负责的交接？

## 时序图

**回答**：在一个具体用例场景中，参与者和稳定职责按什么顺序协作？

规则：

- 标题写明用例与场景，如“提交排程 - 手术间冲突”。
- 参与者从左到右通常为 Actor、入口/边界、用例协调者、领域职责、外部系统。
- 消息表达业务意图，不照抄 HTTP 路径、框架回调或每个私有方法。
- 同步、异步、返回和事件使用一致箭头语义；只画对理解因果关系有价值的返回。
- 使用 `alt/opt/loop/par/break` 表达真实控制语义，并写清 guard。
- 不把数据库当作所有场景的中心参与者；只有数据持久化本身影响决策时才展示。
- 时序图不替代组件图。参与者过多通常意味着场景范围过大或职责边界需要重新检查。

审查问题：谁负责协调用例？领域规则在哪里执行？外部失败如何传播或补偿？消息方向是否暴露循环依赖？

## 组件图

**回答**：哪些稳定职责共同提供能力，它们通过什么接口依赖彼此？

规则：

- 组件按业务能力或稳定职责划分，不按源代码顶层目录机械映射。
- 每个组件写清它拥有的职责和不拥有的职责。
- 使用 provided/required interface 或带标签的依赖表达合同；依赖方向必须明确。
- 数据所有权跟随负责维护不变量的组件，不因共享数据库而模糊。
- 外部系统明确放在边界外，并标注交互目的。
- 只有当进程、节点或网络边界影响当前决策时才加入部署信息；否则保持组件视图纯粹。
- 避免“前端 -> 后端 -> 数据库”式泛化图，它通常不能回答职责与边界问题。

审查问题：是否存在双向依赖、共享可变数据或万能组件？接口是否表达业务能力？改变一个规则需要跨越多少职责边界？

## 状态图

**回答**：一个有重要生命周期的业务实体处于哪些稳定阶段，什么事件允许它转换？

规则：

- 仅用于生命周期影响规则、权限、可见性或外部承诺的实体。
- 状态是持续一段时间并影响允许行为的业务阶段，不是瞬时动作或数据库布尔字段。
- 转换标签采用 `事件 [guard] / action`，至少写清事件。
- 明确初始状态、终止状态和不可逆转换。
- 把超时、取消、失败、恢复和重试纳入审查，但只画领域真实允许的路径。
- 并发区域只用于真正独立的并行状态维度；否则拆成不同实体或图。
- 每个状态都应能回答“此时允许什么、禁止什么、由谁触发离开”。

审查问题：是否存在到不了或离不开的状态？同一事件在不同状态下的结果是否清楚？活动流程是否绕过状态约束？

## 跨图一致性

多张图不要求复制全部信息，但共同术语和承诺必须一致：

- 用例图中的核心目标应能在活动图或时序场景中找到行为解释。
- 活动和时序消息中出现的领域对象应与领域类图采用相同名称和含义。
- 状态转换事件应能追溯到用例、活动步骤或协作消息。
- 时序参与者应能映射到组件职责或外部 Actor，而不是临时发明无主职责。
- 组件接口不应承诺领域模型和流程未支持的能力。

发现不一致时先判断是视图遗漏、术语漂移还是设计冲突；不要靠改名掩盖问题。

## 反模式与审查清单

提交审查前逐项确认：

- [ ] 每张图都有 `arch-lens: type`、`arch-lens: question` 和可读标题。
- [ ] 问题无法由更简单的文字或已有图回答。
- [ ] 候选默认一张、通常不超过三张；超额图已有逐张理由和生成前的人类明确同意。
- [ ] 已优先修改现有图，相近场景没有按 AC 或测试案例机械拆分。
- [ ] 图中主要名称来自领域语言，而非框架或目录结构。
- [ ] 边界、方向、关键关系语义和异常路径足够明确。
- [ ] 没有为了“完整”而加入无决策价值的元素。
- [ ] 假设、候选设计和既有事实没有混在一起。
- [ ] 同一概念在不同图中的名称、责任和生命周期一致。
- [ ] `.puml` 文本 diff 可读，没有大面积纯布局或样式噪声。
- [ ] proposal 和 decisions 说明问题与取舍，但没有用 Markdown 复制图中的模型。
- [ ] 每个持久图集变化已由 Change Pack 声明，并可追溯到 AC 和人工批准。
- [ ] `arch-lens diagrams check` 通过。
- [ ] 已通过 IDE 本地预览或按需 SVG 检查标签、箭头、交叉线、密度和阅读顺序。

常见反模式：把 ERD 当领域模型；把页面清单当用例；把函数调用跟踪当时序设计；把代码包图当组件边界；把流程步骤当状态；把系统部署图当所有架构讨论的默认入口。

## 研究依据

- [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/)：UML 的抽象语义、结构与行为图基础。
- [PlantUML Language Reference Guide](https://plantuml.com/guide)：文本语法和受支持图种的官方入口。
- PlantUML 官方图种文档：[Use Case](https://plantuml.com/use-case-diagram)、[Class](https://plantuml.com/class-diagram)、[Activity](https://plantuml.com/activity-diagram-beta)、[Sequence](https://plantuml.com/sequence-diagram)、[Component](https://plantuml.com/component-diagram)、[State](https://plantuml.com/state-diagram)。
- [PlantUML Security](https://plantuml.com/security)：本地文件和 URL 访问的安全配置依据；Arch Lens 在文本检查之外强制使用 `SANDBOX`，并只通过 stdin 传入自包含模型。
- [《架构师必备技能：如何画好架构图》](https://zhuanlan.zhihu.com/p/344400915)：从现实世界的实体、行为和规则进行抽象，以不同视角降低沟通成本；本文只吸收其建模思想，不采用把系统技术分层当默认产品范围的做法。
- Martin Fowler, [UML Distilled](https://martinfowler.com/books/uml.html)：把 UML 作为选择性沟通工具而非穷尽式规格，强调按目的使用少量图。

这些来源共同支持一个边界：UML 提供建模语义，PlantUML 提供人和 AI 都可读写的文本与标准渲染；Arch Lens 负责问题选择、质量规则和审查工作流，不再实现另一套 UML 引擎或 Viewer。
