# Change Proposal

## Problem And Evidence

当前指南虽然写有“最少必要视图”和“一图一问”，但同时并列六类 UML 视图、强调跨图一致性，并把拆图放在生成规则中。AI 容易把图种列表当作隐形清单，把“一图一问”执行成“每个问题、场景或 AC 各生成一图”。

实际使用已经暴露出这一倾向：notification-platform 的一个一期候选一次生成 13 张图；Arch Lens 自举变更也经常同时触及四至五张图。单张图可能各自合理，但整体阅读、跨图对齐和人工审批成本开始超过它们带来的判断价值。

## Goals

- 让 AI 在写 `.puml` 前先提交最小视图清单，逐张说明问题、决策价值和复用选择。
- 持久建模默认只生成或修改一张主视图，通常不超过三张。
- 第四张及以后必须具有无法由已有图、简单文字或前三张回答的独立判断需求，并在生成前获得人类明确同意。
- 优先修改已有图；相同参与者和责任结构下的正常、失败、重试等场景优先合并表达。
- 把图集规模审查前移到生成阶段，而不是等候选已经大量产生后再清理。

## Non-goals

- 不由 CLI 按文件数机械拒绝模型；是否值得建图仍是 Skill 的语义判断。
- 不规定项目全部历史图集的绝对上限，也不要求为了满足数字删除仍有独立决策价值的图。
- 不限制临时草稿、IDE 预览或 SVG 数量；门禁针对要持久进入 Change Pack 和批准图集的 `.puml`。
- 不改变 PlantUML 图种、语法、安全策略和 Change Pack 审批协议。

## Acceptance Criteria

- AC-001: Skill 明确规定持久建模默认一张主视图、通常最多三张，且图种列表不得被当作完整性清单。
- AC-002: propose change 在写 `.puml` 前必须列出拟生成或修改的视图、各自问题、独立决策价值以及复用已有图的判断。
- AC-003: 第四张及以后必须逐张证明无法合并，并在生成前获得当前会话中的人类明确同意。
- AC-004: 指南要求优先修改已有图，不按 AC 或相近场景逐图生成，并给出合并与拆分的判断规则。
- AC-005: review model 必须检查视图预算、重复问题和可合并图；超额未获授权时返回建模阶段收敛候选。
- AC-006: README、Skill 元数据和静态测试同步表达精简模型集策略，CLI 不新增文件数语义判断。

## Assumptions

- 三张图足以覆盖多数单一变更中的一个主问题及结构、行为两个互补判断。
- 超过三张并非必然错误，因此应使用人类授权的软门禁，而不是 CLI 硬上限。
- 现有 PlantUML 图仍可作为长期模型继续维护，无需按本变更一次性重画或删减。

## Open Questions

- [x] Q001: 超过三张是否一律禁止？不禁止；逐张论证独立判断价值并在人类明确同意后生成。
- [x] Q002: 是否由 CLI 计算并拒绝图数？不采用；文件数不能判断语义价值，CLI 继续只报告确定性事实。
